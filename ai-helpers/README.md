# Cortex-MD: AI Helpers Module

The **AI Helpers** module provides a stepwise execution pipeline designed to isolate the feature development process from the general system context. It allows you to take a high-level idea and transform it into audited code through an iterative, repeatable process.

## 1. What is the Stepwise Execution Pipeline?

While Cortex-MD excels at managing global memory and episodic context, it doesn't prescribe how to do the actual coding *during* the session. The stepwise pipeline divides the software development cycle into five explicit phases.

By separating reasoning (planning) from execution (coding), it prevents "amnesia" in lightweight models and "context bloat" in models working with large context windows.

## 2. Architecture

The module is divided into three areas:

1.  **`/generators/` (The Engines):** Contains the active prompts. These are the tools executed to transform information from one step to the next.
2.  **`/idea-development/` (The Workbench):** The workspace where the idea evolves until it becomes audited code. The `01-brief/` folder acts as an idea backlog: it can contain multiple briefs in parallel.
3.  **`/prompts/` (Orchestration Prompts):** Contains master prompts for automated multi-agent execution.

## 3. Work Modes

There are three main ways to operate with the AI. Choose the option that best fits your desired level of control and the capabilities of the model you are using.

### Option 1: Manual Flow (Total Control)

The user interacts step-by-step with each generator. Ideal for absolute visibility and control over each phase.

1.  Write your requirements in a file within `01-brief/` (e.g., `01-brief/my-feature.md`).
2.  Request to generate the breakdown with `01-generate-breakdown.md` → creates `02-breakdown.md`.
3.  For each PR in the breakdown, invoke `02-generate-spec.md` → creates `03-spec.md`.
4.  Invoke `03-generate-prompt.md` → creates `04-prompt.md`.
5.  Pass that prompt to your coding agent to implement the feature.
6.  Execute `04-generate-audit.md` to verify that the code complies with the specification.
7.  When you decide the session is complete (which can span multiple PRs), execute `.agents/workflows/end.md` to consolidate learnings into the Hippocampus.

### Option 2: Orchestrated Flow (Maximum Automation)

Designed to delegate the complete cycle to an Orchestrator agent with multi-agent coordination (Context Provider, Architect, Code, Debug). `orchestator-memory.md` acts as the shared working memory for the duration of the plan.

**Context configuration for sub-agents:** if your orchestration tool supports context rules by agent or mode (e.g., Zoo Code with `.zoo/rules/` files), configure all agents to automatically read `AGENTS.md` and execute `start.md`. This eliminates the need to copy `conventions.md` in every plan and allows reducing `orchestator-memory.md` to operational state only. See the Context Note in `prompts/breakdown-orchestrator.md` for the complementary focus clause.

1.  Use `01-generate-breakdown.md` to convert the brief into the plan (`02-breakdown.md`).
2.  Invoke your Orchestrator agent and pass it the master prompt `prompts/breakdown-orchestrator.md`.
3.  The Orchestrator executes the complete cycle:
    - **Step 0:** Initializes `orchestator-memory.md` (Context Provider + Architect).
    - **Per PR:** Context Provider scans the area → Architect generates spec/prompt → Code implements, validates, and self-registers in `orchestator-memory.md`.
    - **Final audit:** Debug audits the complete plan against `02-breakdown.md`.
4.  The user supervises and receives the final audited result.
5.  When ready, run `.agents/workflows/end.md` to consolidate into Cortex-MD.

**QA on demand:** once the plan is complete, invoke `prompts/QA.md` to have Architect generate `QA-notes.md` with testing actions grouped by area.

### Option 3: Independent (No Stepwise Pipeline)

The main project agent (with full global context and semantic memory loaded) manages the task directly without using the generators. The user requests global workflows directly, such as `/deep-plan` or `/audit`, relying on the agent's ability to manage the full context without partitioning reasoning into separate files.

> **When to use it?** When the task is small enough or the main agent is capable enough to not need the scaffolding of the pipeline.

## 4. Pipeline Files

### `/idea-development/`

| File | Description |
| --- | --- |
| `01-brief/` | Folder with the user's initial requirements. |
| `02-breakdown.md` | PR plan generated by `01-generate-breakdown.md`. Source of truth for the plan. |
| `03-spec.md` | Technical specification of the current PR (overwritten per PR). |
| `04-prompt.md` | Implementation prompt for the current PR (overwritten per PR). |
| `05-audit.md` | Audit findings for the plan. |
| `orchestator-memory.md` | **[Orchestrated Flow]** Working memory: PR status, anti-redundancy inventory, critical conventions _(optional if the orchestrator auto-injects context)_, and alert notes. Ephemeral per plan. |
| `QA-notes.md` | **[On demand]** Manual QA actions generated by `prompts/QA.md`. |

### `/generators/`

| File | Description |
| --- | --- |
| `01-generate-breakdown.md` | Converts the brief into the PR plan. |
| `02-generate-spec.md` | Generates the technical spec for the current PR. Produces two mandatory sections: **Anti-Redundancy Inventory** and **Validation Commands**. |
| `03-generate-prompt.md` | Generates the implementation prompt for the Code agent. |
| `04-generate-audit.md` | Audits an individual PR against its spec (Manual Flow). |

### `/prompts/`

| File | Description |
| --- | --- |
| `breakdown-orchestrator.md` | Master prompt for the Orchestrated Flow. Coordinates Context Provider, Architect, Code, and Debug across PR cycles. |
| `QA.md` | On-demand prompt. Instructs Architect to generate `QA-notes.md` grouped by UI area, minimizing navigation and repeated actions. |
| `fix-edit-error.md` | Emergency recovery when Code fails editing the same file 3+ times. The Orchestrator injects it automatically via step 1e. |

## 5. Design Rules

### A. Context Barrier (`AGENTS.md` local)

To radically protect the main agent's working memory, this folder contains its own `AGENTS.md`. This acts as a barrier, instructing agents to **ignore** the entire contents of this folder for global automatic indexing. The files here are read and overwritten strictly on-demand, preventing half-finished drafts from contaminating long-term memory.

### B. Unidirectional Barrier

`ai-helpers` consumes files from `.agents/workflows/` and `.agents/memory/`, but **`.agents/` does not know about or reference `ai-helpers/`**. Never modify `.agents/` files from within this module.

### C. Identity and Context Decoupling

By default, sub-agents invoked by the Orchestrator start as "blank slates" with no project memory: `orchestator-memory.md` (including Critical Conventions) is the context vehicle. If your orchestration tool auto-injects base context into each sub-agent, `orchestator-memory.md` reduces to operational state only (PRs and inventory), and a focus clause in each mandate prevents sub-agents from executing irrelevant phases of `start.md`. In the Manual Flow, the user manages it directly.

### D. Full Overwrites — No Cleanup Cost

All pipeline files are overwritten completely (not patched). This eliminates the token cost of stale content and makes cleanup steps between PRs unnecessary. The next plan overwrites `orchestator-memory.md` from scratch at Step 0.

### E. Kanbanization

The `02-breakdown.md` file uses Markdown checkboxes (`- [ ]`, `- [x]`). In the Orchestrated Flow, Code self-registers its completion in `orchestator-memory.md` the same way.

### F. Anti-Redundancy Inventory

The output of `02-generate-spec.md` always includes an **Anti-Redundancy Inventory** section before proposing new abstractions. This forces an explicit check of existing project packages and prevents recreating components, hooks, or utilities that already exist.

### G. Manual Consolidation

When a feature is completed, **it is the user's responsibility** to run `.agents/workflows/end.md` to consolidate learnings into Cortex-MD's semantic memory. This allows grouping multiple PRs into a single episodic session entry rather than consolidating after each individual PR.

## 6. Customization

The prompts in `generators/` and `prompts/` can and should be customized to fit your team's specific tools and conventions. They are simple Markdown files designed to be modified.

> **Note on workflow modes:** Extension workflows (`deep-plan.md`, `audit.md`) support three modes (`strict`, `standard`, `autonomous`). If your team does not use high-capacity reasoning models (Opus, o1, Deep Research), consider **removing `autonomous` mode** from your workflows to reduce cognitive friction in mode selection. Fewer options = less overhead.
